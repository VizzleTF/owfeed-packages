# Как добавлять и обновлять пакеты

*[English version](CONTRIBUTING.md)*

Пакет в этом фиде — **файл со значениями**. Скрипта на пакет нет: качает всех одна общая реализация,
поэтому обновление переписывает данные, а не код, и добавление пакета не начинается с копирования
чужого шелла.

```
packages/<name>/upstream.sh   версия, контрольные суммы, каким ключом подписано
packages/<name>/files/…       по желанию: то, что добавляет сам фид, например init-скрипт
keys/…                        запиненные публичные ключи авторов, чьи пакеты мы несём
owfeed.yml                    запись в packages:, только если owfeed должен собирать
```

---

## Хочу добавить пакет

Какая из двух форм — зависит от того, что публикует апстрим.

### Апстрим публикует готовый `.apk`

Собирать нечего. Фид раздаёт ровно то, что выпустил автор, и добавляет свою подпись.

```sh
# packages/luci-theme-footstrap/upstream.sh
KIND="apk"
REPO="VizzleTF/luci-theme-footstrap"
VERSION="0.11.6-r1"
ARTIFACT="luci-theme-footstrap-0.11.6-r1.apk"
SHA256="e2e7bde2…"

SIG_KEY="keys/vizzletf-release.pub"     # если автор подписывает релизы
SIG_KEY_ID="18c63865e2bcf8d6"
AUTO_MERGE="yes"
```

Это весь пакет. **Записи в `owfeed.yml` нет** — owfeed ничего не собирает.

### Апстрим публикует бинари или отдельные файлы

Пакет собирает owfeed, поэтому файлов два: значения и запись в `owfeed.yml`, описывающая результат.

```sh
# packages/podkop-updater/upstream.sh
KIND="binaries"
REPO="VizzleTF/podkop_autoupdater"
VERSION="0.3.4-r1"
BINARY_DEST="/usr/bin/podkop_updater"

# <артефакт>  <sha256>  <архитектуры OpenWrt, на которых он идёт>
ARTIFACTS="
podkop_updater-amd64  2d64d66c…  x86_64
podkop_updater-arm64  ba045eaa…  aarch64_cortex-a53 aarch64_cortex-a72 aarch64_generic
"
AUTO_MERGE="no"
```

```yaml
# owfeed.yml
- name: podkop-updater
  build: mkpkg
  arch: [x86_64, aarch64_cortex-a53, aarch64_cortex-a72, aarch64_generic]
  version-from: file:./staging/podkop-updater.version
  files: ./staging/podkop-updater/{arch}
  description: "Одна строка. LuCI обрезает после 512 байт."
```

То, что шипает сам фид — init-скрипт, дефолтный конфиг, — кладётся в `packages/<name>/files/` и
копируется в каждую архитектуру.

Статическому бинарю нужен правильный таргет сборки и не нужен OpenWrt SDK, поэтому один артефакт
апстрима обычно покрывает несколько архитектур OpenWrt. Какие именно — это суждение о том, где
реально работают сборки апстрима, и потому оно лежит рядом с пакетом, а не внутри инструмента.

### Какие релиз-линии

Фид обслуживает обе: apk для 25.12 и новее, opkg для 24.10 и старее. Роутеры живут на релизе годами,
так что публиковать только новую линию — оставить большинство установленной базы там, где она была.

**Апстрим публикует оба контейнера.** Запините и второй — он будет обслуживать обе линии из той же
сборки:

```sh
ARTIFACT="luci-theme-footstrap-0.11.6-r1.apk"
SHA256="e2e7bde2…"
ARTIFACT_IPK="luci-theme-footstrap_0.11.6-r1_all.ipk"
SHA256_IPK="3255edc1…"
```

**Собирает owfeed** (`KIND="binaries"`). Делать нечего: оба формата выходят из одного
подготовленного payload'а.

**Пакет только для одной линии.** Скажите об этом в `owfeed.yml` — и в индексе другой линии его не
будет вовсе, а не «будет, но не поставится»:

```yaml
- name: luci-app-mine
  releases: ["25.12"]
```

### Дальше

```sh
./tools/fetch.sh packages/<name>
owfeed build && owfeed sign && owfeed index && owfeed doctor --require-origin
owfeed smoke                 # 25.12, на настоящем роутере
owfeed smoke --release 24.10 # 24.10, на настоящем роутере
```

Откройте pull request. CI выполняет ровно это, но одноразовым ключом — так что из форка к ключу
фида ничто не приближается.

## Хочу обновить пакет

Обычно не нужно. Ежечасная задача спрашивает каждый апстрим про свежий релиз и открывает PR за вас,
пересчитав суммы из байт, которые релиз реально отдал.

Руками: поправьте `VERSION` и суммы в `upstream.sh`. Больше ничего не меняется.

```sh
./tools/fetch.sh packages/<name>     # упадёт, если сумма не сошлась
```

## Хочу, чтобы обновлялось само

`AUTO_MERGE="yes"` просит GitHub смержить обновление, когда проверки пройдут.

Он доступен **только там, где апстрим публикует отделённую подпись** рядом с артефактом, и эта
подпись проверяется против ключа, запиненного в `keys/`. Это ручательство от кого-то, кроме самого
фида. Где апстрим публикует только суммы, обновление ждёт человека: сумма от того же хоста, что и
артефакт, говорит, что скачалось без повреждений, а не что файл не подменили.

Проверки не пропускаются ни в том, ни в другом случае.

## Я собираю в своём CI и хочу свой пакет в этом фиде

Вы не пушите в этот фид, и это намеренно. Публикация сюда требовала бы либо ключа подписи фида, либо
доступа на запись — а любое из двух позволило бы каждому участнику опубликовать под именем фида что
угодно, включая версию `dropbear` повыше.

Поэтому через границу не переходит ничего:

```
ваш репозиторий                              этот фид
───────────────                              ────────
owfeed build                                 раз в час: видит ваш релиз
owfeed sign          ← ваш ключ              проверяет вашу подпись по keys/
публикуете релиз     ──────────────────────► добавляет свою подпись
                                             индексирует, публикует
```

Вы никогда не держите ключ фида. Фид никогда не держит токен к вашему репозиторию.

**Ваша подпись не срезается.** Блоки подписей в apk складываются, поэтому пакет, который ставит
роутер, несёт и вашу, и подпись фида. Подписчик, поставивший ещё и ваш публичный ключ, проверит вас
напрямую; тот, кто доверяет только фиду, работает как обычно.

### На вашей стороне

[`examples/gitlab-ci.yml`](examples/gitlab-ci.yml) и [`examples/owfeed.yml`](examples/owfeed.yml) —
рабочая пара. Коротко:

```sh
owfeed build
owfeed sign                       # ваш ключ, из masked-переменной CI
owfeed doctor --require-origin    # каждый пакет называет свой репозиторий
owfeed smoke                      # ставится на живой образ OpenWrt
# публикуете dist/ как ассеты релиза
```

`--require-origin` — не формальность. `url:` уезжает в индекс и показывается `apk info` на роутере,
то есть это единственное, что говорит пользователю, кто опубликовал то, что он поставил.
`repo-commit: env:CI_COMMIT_SHA` записывает, из какого коммита это собрано.

### На этой стороне

Один pull request, однократно: `packages/<name>/upstream.sh` с вашим репозиторием, вашим публичным
ключом и первым пином — плюс ваш ключ в `keys/`. Дальше ежечасная задача следит за вашими релизами и
открывает обновления сама.

Добавление вашего ключа — тот самый диф, который заслуживает второго взгляда, так что его будут
читать внимательно. Это момент, когда фид решает за вас поручиться; всё после него механическое.

## Что проверки не пропустят

`owfeed doctor` и `owfeed smoke` стоят на каждом PR. Что чаще всего ловится с первого раза:

| | |
|---|---|
| `arch: all` | apk считает такой пакет неустанавливаемым. Нужно `noarch`. |
| `/etc/config/foo` шипается, но не в `conffiles:` | sysupgrade молча заменит настройки пользователя вашими дефолтами при каждом обновлении прошивки. |
| `.po` в payload | LuCI читает скомпилированные `.lmo`. Укажите `i18n.from:`. |
| Версия, которую apk не разберёт | после `~` только hex, `-r<n>` последним. |
| Пакет, который собирается и не ставится | `smoke` ставит фид на живой образ OpenWrt и падает, если apk попросит `--allow-untrusted`. |

Каждая находка говорит, чем это грозит и что делать.

## Зачем пин и зачем ключ

**Всё скачанное пинуется по sha256 в этом репозитории.** Сумма, отданная тем же хостом из того же
релиза, проверкой не является — кто может подменить одно, подменит и другое. Пин, записанный здесь,
является: он появился в момент, когда на него посмотрел человек.

**Где автор подписывает — подпись тоже проверяется**, против ключа из `keys/`. Пин доказывает, что
байты не менялись с тех пор, как их кто-то видел; подпись говорит, кто их произвёл. Только второе
может оправдать автомерж.

Всё в этом фиде подписано ключом **фида**, а не авторов. Это не предпочтение: apk берёт доверие из
подписанного индекса, а подписать индекс, описывающий всё содержимое фида, может только сам фид.
Подписывать пакеты ключами авторов означало бы поставить ключ каждого автора на каждый роутер, и
каждый такой ключ стал бы trust anchor для **любого** имени пакета, а не только для его собственных.

Поэтому подпись фида стоит ровно столько, сколько было проверено до её наложения. Ради этого все
правила выше и существуют.
